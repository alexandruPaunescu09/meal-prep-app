## Database Schema

### Enums
- `meal_type`: breakfast, lunch, dinner, snack

### Tables

**`ingredient_categories`**
- `id` UUID PK, `slug` TEXT UNIQUE, `name` TEXT, `sort_order` INT
- `created_at` TIMESTAMPTZ
- Index: `(sort_order)`

**`ingredients`**
- `id` UUID PK, `name` TEXT, `brand` TEXT (nullable), `category` TEXT (references ingredient_categories.slug by convention)
- `quantity_purchased` NUMERIC, `unit` TEXT (g/ml/buc), `package_price` NUMERIC **nullable (RI-0c: NULL = price pending, so the generated `price_per_unit` is NULL too; `quantity_purchased` stays NOT NULL)**
- `price_per_unit` NUMERIC **GENERATED** (`package_price / NULLIF(quantity_purchased, 0)`)
- `piece_weight_g` NUMERIC NULL, CHECK `> 0` (`20261030000000`): grams per 1 `buc`, only meaningful when unit = 'buc'; nutrition math turns pieces into grams with it (assumes nutrition is per 100 g). Exposed on `ingredients_public` (still no price/notes columns)
- Macros (per 100g): `calories`, `protein`, `carbs`, `fat`, `fiber`, `sugar`, `sat_fat`, `salt`
- `micronutrients` JSONB, `api_source` TEXT, `barcode` TEXT
- `created_at`, `updated_at` TIMESTAMPTZ (trigger-maintained)

**`recipes`**
- `id` UUID PK, `name` TEXT, `portions` INT (default 1), `final_weight` NUMERIC (nullable), `notes` TEXT
- `container_type_id` UUID FK→container_types SET NULL
- `source_url` TEXT NULL (CHECK `~* '^https?://'`), `instructions` JSONB NOT NULL DEFAULT `'[]'` (array of 1–500 char strings, max 40; CHECK `recipe_instructions_valid`) — RI-0b, admin-only: NOT in `recipes_public`, never sent to customers

**`recipe_ingredients`** (junction)
- `recipe_id` FK→recipes CASCADE, `ingredient_id` FK→ingredients RESTRICT, `quantity` NUMERIC

**`clients`**
- `id` UUID PK, `name` TEXT, `email` TEXT, `phone` TEXT
- `calorie_target` INT, `weight_kg` NUMERIC, `target_weight_kg` NUMERIC (nullable, CHECK 30–300; goal weight), `restrictions` TEXT, `allergies` TEXT, `preferences` TEXT, `notes` TEXT
- `container_tolerance` INT (default 2) — max containers a client can have outstanding before being flagged

**`meal_plans`**
- `id` UUID PK, `name` TEXT, `client_id` FK→clients SET NULL, `week_start` DATE, `markup_multiplier` NUMERIC (default 2.5)
- `calorie_target` INT (kcal/day), `protein_per_kg` NUMERIC, `fat_per_kg` NUMERIC — per-plan nutrition targets; macros multiply by `clients.target_weight_kg` when set, else `clients.weight_kg`. Carbs and fiber targets are derived (carbs from calories−protein−fat; fiber as 10–14 g/1000 kcal range).

**`meal_plan_entries`**
- `meal_plan_id` FK→meal_plans CASCADE, `day_of_week` INT (1-7), `meal_type` meal_type
- `recipe_id` FK→recipes RESTRICT (nullable), `ingredient_id` FK→ingredients RESTRICT (nullable), `quantity` NUMERIC (nullable)
- `portions` NUMERIC (supports fractional)
- CHECK: `recipe_id IS NOT NULL OR ingredient_id IS NOT NULL`

**`ingredient_price_history`**
- `ingredient_id` FK→ingredients CASCADE, `package_price`, `quantity_purchased`, `unit`, `price_per_unit`, `recorded_at`
- Index: `(ingredient_id, recorded_at DESC)`

**`container_types`**
- `id` UUID PK, `name` TEXT, `volume_ml` INT, `cost` NUMERIC (replacement cost in lei)
- `created_at` TIMESTAMPTZ

**`container_deliveries`**
- `id` UUID PK, `client_id` FK→clients CASCADE, `meal_plan_id` FK→meal_plans SET NULL
- `delivery_date` DATE, `notes` TEXT, `created_at` TIMESTAMPTZ
- Index: `(client_id, delivery_date DESC)`

**`container_delivery_items`**
- `id` UUID PK, `delivery_id` FK→container_deliveries CASCADE, `container_type_id` FK→container_types RESTRICT
- `quantity_sent` INT, `quantity_returned` INT

**`prep_rules`**
- `id` UUID PK, `ingredient_category` TEXT (nullable), `ingredient_id` FK→ingredients CASCADE (nullable)
- `prep_type` TEXT, `advance_days` INT, `time_estimate_minutes` INT (nullable), `notes` TEXT (nullable)
- CHECK: `ingredient_category IS NOT NULL OR ingredient_id IS NOT NULL`
- Index: `(ingredient_category)`, `(ingredient_id)`

**`prep_tasks`**
- `id` UUID PK, `week_start` DATE, `prep_date` DATE, `cook_date` DATE
- `ingredient_id` FK→ingredients CASCADE, `prep_type` TEXT, `quantity` NUMERIC, `unit` TEXT
- `recipe_names` TEXT[], `completed` BOOLEAN, `completed_at` TIMESTAMPTZ (nullable)
- Index: `(week_start, prep_date)`

**`shopping_check_state`**
- `week_start` DATE, `ingredient_id` FK→ingredients CASCADE, `checked_at` TIMESTAMPTZ
- PK: `(week_start, ingredient_id)`. Row presence = checked. Persists shopping-list check-offs across reloads; keyed per week so checks are shared across all plans for that week.
- Index: `(week_start)`

**`cooking_check_state`**
- `week_start` DATE, `recipe_id` FK→recipes CASCADE, `checked_at` TIMESTAMPTZ
- PK: `(week_start, recipe_id)`. Row presence = recipe marked cooked. Same pattern as `shopping_check_state`, keyed per week so checks are shared across all plans for that week.
- Index: `(week_start)`

**`foods`** (shared consumer-product catalog, no prices; customers never write)
- `id` UUID PK, `barcode` TEXT UNIQUE (nullable), `name` TEXT, `brand` TEXT, `unit` TEXT ('g'|'ml')
- Per 100 g/ml: `calories`, `protein`, `carbs`, `fat`, `fiber`, `sugar`, `sat_fat`, `salt`, `micronutrients` JSONB
- `serving_size` NUMERIC (>0), `serving_label` TEXT, `package_size` NUMERIC
- `source` ('off'|'label_photo'|'admin'), `status` ('active'|'pending'|'hidden'), `created_by_client_id` FK→clients SET NULL, `verified_at`, `promoted_ingredient_id` FK→ingredients SET NULL
- Indexes: `lower(name)`, `(status)`, `(created_by_client_id, created_at DESC)`. RLS: admin ALL; customer SELECT when `current_client_id() IS NOT NULL AND (status='active' OR (status='pending' AND created_by_client_id = current_client_id()))`; no customer writes (inserts go through `/api/portal/foods/*` with the service client).
- `label_photo_path` / `front_photo_path` TEXT (nullable, `20261019000600_food_diary_shared_schema.sql`): storage keys in the private `food-label-photos` bucket for label-photo foods. Path convention `{client_id}/{food_id}/label.jpg` / `front.jpg` (food_id may be client-generated before the row exists); storage RLS: customer read/write only inside their own `client_id` folder, admin full access.

**`rate_limit_hits`** (service-role only; RLS on, no policies, no grants)
- `bucket` TEXT, `key_hash` TEXT (SHA-256 of the caller IP, never raw), `created_at`; index `(bucket, key_hash, created_at DESC)`. Written only by `check_rate_limit`.

**`food_label_parses`** (label-photo parse log, for the FD-5 daily limit)
- `id` UUID PK, `client_id` FK→clients CASCADE, `model` TEXT, `outcome` ('ok'|'unreadable'|'error'), `created_at`
- Index `(client_id, created_at DESC)`. RLS: admin SELECT only; written server-side with the service client.

**`food_favorites`** (a customer's starred catalog items, FD-6)
- `id` UUID PK, `client_id` FK→clients CASCADE, exactly one of `food_id` / `ingredient_id` / `recipe_id` (FKs CASCADE; CHECK `num_nonnulls(...) = 1`), `created_at`
- Partial UNIQUE per target: `(client_id, food_id)`, `(client_id, ingredient_id)`, `(client_id, recipe_id)`. RLS: customer ALL on own rows; admin ALL (FD-12's food merge repoints favorites to the surviving food).

**`food_log_entries`** (customer food diary)
- `id` UUID PK (generated client-side so offline replays upsert idempotently), `client_id` FK→clients CASCADE, `log_date` DATE (customer LOCAL date), `meal_type` meal_type
- `source_kind` ('food'|'ingredient'|'recipe'|'quick'), `food_id` / `ingredient_id` / `recipe_id` FKs all SET NULL (history survives deletions); CHECK at most one FK, none for quick
- `quantity` NUMERIC >0, `quantity_unit` ('g'|'ml'|'serving'|'portion')
- Nutrition SNAPSHOT (totals for this entry, not per 100): `name`, `brand`, 8 nutrient columns, `micronutrients` JSONB — computed server-side at log time.
- Index `(client_id, log_date)`. RLS: customer ALL on own rows; admin SELECT.

**`meal_entry_status`** (customer eaten/skipped per plan entry)
- PK `meal_plan_entry_id`, `client_id`, `status` ('eaten'|'skipped'), `updated_at`
- `portion_factor` NUMERIC NULL, CHECK `> 0 AND <= 5` (`20261019000300_meal_status_portion_factor.sql`): share of the planned portion actually eaten ("Ate a different amount"); NULL = 1×. Only meaningful while `status='eaten'`; `/api/portal/status` stores NULL for any other status.

**`weight_logs`** (customer weight log, FD-9)
- `id` UUID PK, `client_id` FK→clients CASCADE, `log_date` DATE (customer LOCAL date), `weight_kg` NUMERIC CHECK 20–300, `created_at`, `updated_at` (trigger)
- `UNIQUE (client_id, log_date)` (a second log the same day upserts). RLS: customer ALL on own rows (`current_client_id()`); admin ALL.

**`invoices`** (admin-only)
- `id` UUID PK, `store` TEXT, `invoice_date` DATE, `total` NUMERIC, `file_names` TEXT[], `parsed` JSONB (raw model output), `applied_lines` JSONB, `model` TEXT, `created_at`
- Index: `(store, invoice_date)`. Rows are written ONLY when the admin approves an import (via `apply_invoice_prices`).

**`ingredient_aliases`** (admin-only)
- `id` UUID PK, `ingredient_id` FK→ingredients CASCADE, `store` TEXT, `alias` TEXT (receipt/invoice name), `created_at`
- UNIQUE `(store, lower(alias))`; index `(ingredient_id)`. Remembers how a store prints an ingredient name.

### Functions
- `apply_invoice_prices(p_invoice jsonb, p_lines jsonb) RETURNS jsonb` — `SECURITY INVOKER`, admin-only (`is_admin()` else raises `forbidden`; EXECUTE revoked from PUBLIC, granted to `authenticated`). Validates each line (ingredient_id present, `package_price` and `quantity_purchased` non-NULL and > 0, else raises and rolls everything back). Atomically inserts the `invoices` row, and for each line: if `package_price` or `quantity_purchased` differs from the stored values it ALWAYS updates both (counted as `updated`), otherwise counts `unchanged`; the OLD values are logged to `ingredient_price_history` only when the stored price is NOT NULL and price-per-unit differs (exact comparison, so a pure package-size change writes no history). A price-pending ingredient (NULL stored price, RI-0c, `20261030000200_price_pending.sql`) is updated and counted `updated` but gets no history row (no bogus 0). Upserts the `(store, raw_name)` alias. Returns `{invoice_id, updated, unchanged}`. Never writes the generated `price_per_unit`.
- Atomic UI write RPCs (`20261018000000_ux_integrity_rpcs.sql`, same house pattern: `SECURITY INVOKER`, `is_admin()` guard, EXECUTE revoked from PUBLIC / granted to `authenticated`; TS payload types in `lib/supabase/types.ts`):
  - `save_recipe(p_recipe_id uuid, p_recipe jsonb, p_ingredients jsonb) RETURNS uuid` — insert (id null) or update a recipe and replace its `recipe_ingredients` in one transaction. Missing `p_recipe` keys are written as NULL, so callers always send every key. Since RI-0b `p_recipe` also carries `source_url` (blank → NULL) and `instructions` (JSON array, missing → `'[]'`, non-array raises `instructions must be a JSON array`); both callers (`recipe-form.tsx`, clone in `recipes-client.tsx`) send them. Form/step helpers in `lib/recipes/steps.ts`.
  - `duplicate_meal_plan(p_source_id, p_name, p_client_id, p_week_start, p_markup_multiplier) RETURNS uuid` — copies the plan's nutrition targets + all entry content (not statuses/reviews).
  - `clone_week(p_source_week date, p_target_week date) RETURNS jsonb` — duplicates every plan of a week; skips clients that already have a plan in the target week. Returns `{created: uuid[], skipped}`.
  - `log_container_delivery(p_client_id, p_meal_plan_id, p_delivery_date, p_notes, p_items jsonb) RETURNS uuid` — delivery + items in one insert; all-zero items skipped.
  - `regenerate_prep_tasks(p_week_start date, p_tasks jsonb) RETURNS jsonb` — replaces a week's prep tasks; new tasks inherit `completed`/`completed_at` from an old task with the same `(ingredient_id, prep_type, prep_date)`. Returns `{inserted, preserved_completed, dropped_completed}`.
  - `save_imported_recipe(p_recipe jsonb, p_ingredients jsonb, p_aliases jsonb) RETURNS uuid` (`20261030000300_save_imported_recipe.sql`, RI-3) — house pattern. Creates the recipe through `save_recipe(NULL, ...)` (source_url / steps handling stays in one place) and upserts `{alias, ingredient_id}` rows into `ingredient_aliases` with the fixed store `'recipe'` (on a `(store, lower(alias))` conflict the alias is repointed), all in one transaction: an unknown ingredient id or alias target rolls back the recipe and every alias. TS types `SaveImportedRecipeAlias` + `SaveRecipeInput`. pgTAP in `supabase/tests/05_save_imported_recipe.sql`.
- `merge_foods(p_from uuid, p_into uuid) RETURNS jsonb` (`20261019000800_merge_foods.sql`, FD-12) — merges a duplicate catalog food into the survivor `p_into`. **`SECURITY DEFINER`** (the one exception to the house INVOKER pattern) with the `is_admin()` guard and a pinned `search_path`: the admin may only READ customers' `food_log_entries`, so instead of a broad admin UPDATE policy on diary rows only this function can repoint them. Rejects `p_from = p_into`, missing rows, and a `p_into` that is not `active` (merging into a pending/hidden food would hide the product from other customers). Repoints `food_log_entries.food_id` (nutrition snapshots untouched) and `food_favorites.food_id` (first deleting `p_from` favorites for clients who already favour `p_into`, because of the partial unique index); moves `p_from`'s barcode to `p_into` only when `p_into` has none (cleared on `p_from` first, UNIQUE); then deletes `p_from` (its photos, `promoted_ingredient_id` and verification are not carried over). Returns `{entries, favorites_moved, favorites_dropped, barcode_moved}`. The function raises if any diary entry is left pointing at `p_from` (deleting it would otherwise null their `food_id`). The migration also drops a broad "Admin repoint food" UPDATE policy that an earlier draft created on local databases.
- Abuse limits (`20261020000000_abuse_limits.sql`, **service_role only**: EXECUTE revoked from PUBLIC/anon/authenticated, `SECURITY INVOKER`, per-key `pg_advisory_xact_lock`): `check_rate_limit(p_bucket, p_key_hash, p_limit, p_window) RETURNS boolean` (records a hit when allowed; used by `/api/intake`, 5 per hashed IP per hour; opportunistic cleanup of rows older than a day); `create_food_with_quota(p_client_id, p_food jsonb, p_limit) RETURNS uuid` (atomic 30 new foods per client per 24 h; NULL = over quota, barcode unique conflict 23505 propagates); `reserve_label_parse(p_client_id, p_model, p_limit) RETURNS uuid` (atomic 10 label parses per client per 24 h, NULL = over limit).
- The same migration adds `meal_reviews` policy "Customer delete own" (`client_id = current_client_id()`; `meal_review_tags` cascade).

### RLS
**Every new table's policies (and every new admin RPC guard) need pgTAP tests in `supabase/tests/` (`npm run test:db`, run in CI): cover own-rows-only, cross-customer denial, admin access and anon denial; wrap each file in `BEGIN; ... ROLLBACK;`.** Plan-entry ownership (`20261020000200`): customer policies on `meal_entry_status` (ALL) and `meal_reviews` (INSERT, UPDATE) require `client_id = current_client_id() AND owns_plan_entry(meal_plan_entry_id)` in USING and WITH CHECK; `owns_plan_entry(uuid)` is a SECURITY DEFINER helper (revoked from PUBLIC/anon, granted to authenticated; the policies are `TO authenticated` so anon never evaluates it). New customer policies keyed on a plan entry must use it. `meal_reviews` "Customer delete own" is unchanged.

Role-aware (since `20260609000001_rls_role_aware.sql`): admin tables use `is_admin()` for full CRUD; customer-readable tables additionally allow reads via `current_client_id()` (portal users). `profiles.role` ('admin' | 'customer') drives both helpers. New tables must follow this pattern.

**`profiles.whats_new_seen`** (TEXT, nullable; `20261020000100_whats_new.sql`): id of the last "What's new" release the customer acknowledged (a `RELEASES` id from `lib/portal/whats-new.ts`). Customers have NO UPDATE policy on `profiles` (it holds `role`); it is written only by `POST /api/portal/whats-new` with the service client.

**Customer-safe views (`20261019000010_hide_prices_from_customers.sql`):** customers have NO direct SELECT on `ingredients` or `recipes` (admin and customers share the `authenticated` role, so column grants cannot hide `package_price` / `price_per_unit` / `quantity_purchased` / `notes`). They read `ingredients_public` and `recipes_public` instead: owner (definer) views with `WHERE is_admin() OR current_client_id() IS NOT NULL`, granted to `authenticated` only. Never add price or notes columns to them. `recipe_ingredients` keeps its customer read policy. Portal code embeds `recipes_public` / `ingredients_public` (PostgREST resolves the embeds through the base-table FKs) and uses `PublicIngredient` / `PublicRecipe` / `PortalEntry` from `lib/supabase/types.ts`.

## Auth & Routing

- **Proxy** (`proxy.ts`, renamed from `middleware.ts` in Next 16): Checks Supabase auth on every request
- **Protected**: All routes under `app/(authenticated)/`
- **Public**: `/login`, `/intake`, `/api/intake`
- **Flow**: No user → redirect `/login`; User on `/login` → redirect `/`
- **Session**: Cookie-based via @supabase/ssr

## API Routes

| Endpoint | Method | Auth | Purpose |
|----------|--------|------|---------|
| `/api/nutrition/search?q=` | GET | Yes | Search USDA + OFF: `{ results, usdaQuery (English query USDA was asked when a Romanian query was translated, else null), sources: { usda: "ok"\|"error"\|"disabled", off: "ok"\|"error" } }` (a failed source is reported, never silently `[]`; "disabled" = no/placeholder `USDA_API_KEY`) |
| `/api/nutrition/barcode?code=` | GET | Yes | Barcode (8-14 digits): `{ existing: {id,name} }` if already saved, else `{ product: BarcodeLookup }` from OFF v2, or 404 `{ error: "not_found" }` |
| `/api/invoices/parse` | POST | Admin | Stateless: multipart `files` (≤10, ≤4 MB, jpeg/png/webp/pdf) → Claude extraction + catalog matching; no writes |
| `/api/invoices/apply` | POST | Admin | JSON `{invoice, lines}` → `apply_invoice_prices` RPC (atomic), revalidates ingredients cache |

- `formatLei` (ro-RO, grouped: "1.234,50 lei"), `formatNumber` (ro-RO decimal comma, no thousands grouping: "2200"), `formatQuantity` (<1 → one decimal, else integer), `formatPricePerUnit(ppu, unit)` (lei/kg, lei/l, lei/buc), `formatCost(total, unpricedCount)` (RI-0c: "23,40 lei" when complete, "≥ 23,40 lei · 2 without a price" when some ingredients are price pending, "Price pending" when none is priced; use it for every cost/selling-price display), `parseDecimal` (accepts "12,5" and "12.5")
- Labels: `humanizeSlug` ("bread_pasta" → "Bread Pasta", fallback when no category name), `WEEKDAYS_SHORT` / `WEEKDAYS_LONG` (Monday-first, index = `day_of_week - 1`)
- Dates in English en-GB: `formatDate`, `formatShortDate`, `formatDateTime`, `formatWeekRange` ("19–25 Oct 2026")
- Local-date helpers returning `'YYYY-MM-DD'`: `toLocalISODate`, `mondayOf`, `addDays`, `currentWeekStart`, `nextWeekStart`, `isMonday`, `parseLocalDate` — canonical here; `lib/portal/entry-helpers.ts` only re-exports aliases. Never use `toISOString()` / `new Date("YYYY-MM-DD")` for calendar dates (UTC off-by-one in Romania).

### Client helpers
- `lib/browser.ts`: `printHtml(html)` (hidden-iframe print), `escapeHtml`, `copyText(text) → Promise<boolean>`
- `lib/hooks/use-listbox-nav.ts`: `useListboxNav({ count, onSelect, onEscape?, enabled?, listRef? })` — ArrowUp/Down/Enter/Escape + `aria-activedescendant` ids for search pickers
- URL state in client components: `router.replace(url, { scroll: false })`, never `window.history.replaceState` (a later `router.refresh()` restores the router's own URL)

### Nutrition Search Pipeline
1. Parallel search: USDA + OFF. `searchNutrition` returns `{ results, sources, usdaQuery }`; each source is `ok` / `error` (and USDA `disabled` without a key). The modal shows an inline notice + Retry for `error` and a quiet note for `disabled`; it aborts superseded requests.
2. USDA: filters cooked entries (unless query asks for cooked), assigns confidence by dataType. Two requests run in parallel and are merged de-duplicated by `fdcId`: (a) the default one (pageSize 15) with NO `dataType` filter on purpose, because USDA's gateway returns a random nginx 400 for ~60% of requests that include "Survey (FNDDS)" in `dataType`; (b) `dataType=Foundation,SR%20Legacy` (no parentheses, measured 8/8 ok, pageSize 100), because (a) is crowded by branded items and dishes so generic raw entries ("Rice, white, ..., raw") never reached the pool (USDA's own order is poor: raw rice is ~55th of 141). If one call fails the other's results are shown, `sources.usda` is `error` and nothing is cached; if both fail it throws.
3. OFF search uses Search-a-licious (`https://search.openfoodfacts.org/search`, `fields` honoured), NOT the legacy `cgi/search.pl` (answered ~80% with 503). Query = sanitized input (Lucene specials and AND/OR/NOT stripped, `sanitizeSearchQuery`) + `countries_tags:"en:romania"`; if that yields < 3 usable products, one more query without the country term is merged in (de-duplicated by barcode). The index does NOT return `nutrition_data_per`, `ingredients_text` or `image_nutrition_url`: the per-100g filter is skipped for search hits and the NCS verification component uses a neutral base (0.4, +0.25 with a brand) via `searchIndex`; kJ-only products get kcal derived (kJ/4.184). `lookupBarcode` still uses the v2 product API. Filters: rejects >2 missing core nutrients; NCS only affects ranking (there is no hard reject).
4. Retry once (300 ms backoff) on network errors / timeouts / 5xx for both sources (`lib/nutrition/http.ts`), never on 4xx; 4 s per attempt by default (`fetchWithRetry(url, init, timeoutMs)`), 8 s for USDA's large Foundation/SR Legacy request (1-3.5 MB; measured median 0.9 s, max 1.8 s, one transient 4 s timeout). Worst case for a search is that request failing twice: 2 x 8 s + 0.3 s, run in parallel with OFF (2 x 4 s + 0.3 s), so about 16.3 s.
5. Cache (`lib/nutrition/search-cache.ts`): bounded in-memory LRU (200 entries), 24 h TTL, per source + normalised query (trim, lowercase, collapse spaces). Only complete successes are stored (errors, and OFF results whose global fallback failed, are never cached, so a repeat retries). Per-instance on Vercel (not shared); `unstable_cache` is deprecated in Next 16 and needs a request context.
6. Ranking (`computeRank`): confidence×45 + nameRelevance×35 (diacritic- and comma-insensitive, so "Chicken, breast" = "chicken breast"; OFF relevance also counts the brand) + USDA bonus(10) - composite penalty(15). For unbranded USDA entries, extra nudges toward the plain generic food: leading comma segments made of query words (+10 all query words, +5 head only; "Rice, white, raw" yes, "Adobo, with rice" / "Rice crackers" no), +4 "raw", +2 "whole", -4 for a derivative word the query did not ask for (dried, powder, flour, oil, juice, frozen, sliced...), -1.5 per comma segment beyond 4. **Brand queries** (Romanian words recognised AND unknown words left, e.g. "lapte zuzu"): USDA only saw the generic words, so USDA gets NO bonuses and an OFF product carrying every unknown word in its name or brand gets +40 and ranks above generic USDA hits. Queries without unknown words ("piept de pui", "chicken breast") keep USDA-generic-first. Ties break by name, brand, barcode, source (`compareStable`) so repeat searches are identical
7. Romanian to English for USDA only (`lib/nutrition/ro-en-terms.ts`, `toUsdaQuery`): USDA only understands English, so its query is translated with a built-in word list (no AI, no external API: free and deterministic). Input is folded (lowercase, no diacritics); phrases beat words (longest match first, e.g. "carne tocata de vita" = ground beef); fillers (de, cu, la...), numbers, percentages and pack sizes are dropped (a percentage becomes nonfat / low fat / whole only for milk, yogurt, kefir); a small PASSTHROUGH set of English words (feta, cod, tofu...) survives next to Romanian ones. If at least one word mapped, UNMAPPED words (usually brands) are dropped and logged with `console.info("nutrition search: unmapped RO words", words)` (words only) so the list can grow from Vercel logs; if nothing mapped the query is sent as typed, so English queries are never altered. OFF always gets the original query. The USDA cache key is the English query. Ranking name relevance uses the English query for USDA results and the original for OFF results. `usdaQuery` (the English query, or null when untranslated) is returned and the modal shows "USDA searched for ...". **Adding terms:** append `romanian = english` to `PHRASE_LINES` / `WORD_LINES` (no diacritics, list every plural/articled form); never add a key that is also an English food word (corn, paste, prune, cod, banana, natural...): `ro-en-terms.test.ts` fails on collisions against its English food word list.
8. Returns top 15

## Patterns

### Forms
- Modal dialogs (fixed overlay), client components
- Submit → Supabase mutation → `router.refresh()` → close modal
- Validation via Zod schemas

### Data Fetching
- **Server components**: Fetch in page.tsx via `createServer()`, pass as props
- **Client components**: `useEffect` or event handlers via `createClient()`

### Modals & feedback
- Use `components/ui/modal.tsx` (never a hand-rolled `fixed inset-0` div); pass `dirty` on forms with unsaved edits. Z-index scale: sidebar overlay z-40, modal z-50, confirm z-[60], toast z-[70].
- No `window.alert/confirm/prompt` (some embedded browsers suppress them): use `useConfirm()` and `useToast()`. Check every Supabase write's `error` and surface failures with a toast (Retry where cheap); optimistic updates roll back on failure.
- Multi-row writes that must succeed together go through an RPC (see Functions), not sequential client calls.
- Deep links: `/recipes/import?url=<link>` fills the URL and starts parsing on load, `?new=1` opens the create form on ingredients/recipes/clients, `?edit=<id>` on ingredients/recipes, `?scan=1` on ingredients; `/meal-plans?client=&week=&new=1`; cards are anchorable as `/clients#client-<id>` and `/containers#client-<id>`.

### Customer catalog reads
- Customers have no direct read on `ingredients` / `recipes`. Customer API routes call `requireCustomer()` FIRST, then read catalog data via `createServiceClient()` with explicit price-free column lists; writes to customer-owned tables use the customer's RLS client.

### Release notes ("What's new" pop-up)
- To announce a feature, add a NEW entry at the TOP of `RELEASES` in `lib/portal/whats-new.ts` (unique `id`, `date` = today as `YYYY-MM-DD`, items with a lucide icon, short English copy using the real UI labels, optional `href`). Customers whose account predates `date` and whose `whats_new_seen` is older see the pop-up once on their next portal load; several unseen releases are shown together, newest first. Never rename or reuse an id. Account age is compared by Europe/Bucharest calendar day. Escape/backdrop count as seen (intentional). The seen POST is silent: a network failure or non-2xx just means the sheet shows again next visit (no toast). "Show me" links to the page the customer is already on are hidden.

### Responsive
- Desktop: tables with expandable rows, sidebar always visible
- Mobile: card layouts (`md:hidden` / `hidden md:block`), hamburger sidebar
- Mobile/PWA (customer portal, installed on iPhone/Android): inputs/selects/textareas are `text-base md:text-sm` per field (under 16px makes iOS zoom on focus; no global unlayered rule, it would beat Tailwind utilities); the app is light-only (`viewport.colorScheme: "only light"`, `html` has a light background + `color-scheme: light`, no dark tokens, otherwise overscroll/pinch-zoom shows black and Android forces dark); `overscroll-behavior: none` on html/body and `overscroll-contain` on every scroll area inside a sheet (`Modal` locks only `html` overflow, never `body`: body is `h-full`, so body:hidden would clip it at viewport height and the scrolled page would jump to the top); `min-h-dvh`, never `min-h-screen`; `env(safe-area-inset-*)` is 0 unless the viewport has `viewportFit: "cover"` (top bar, bottom tabs, sheets and toasts rely on it). Pinch-zoom stays allowed (no `maximumScale` / `userScalable`); do not put `overflow-x: hidden` on html/body (breaks the sticky top bar).

## Business Logic

### Pricing
- All prices in **lei** (Romanian currency)
- `price_per_unit` = package_price / quantity_purchased (DB-generated column)
- Recipe cost = sum(ingredient quantity × price_per_unit)
- Meal plan selling price = weekly ingredient cost × markup_multiplier (default 2.5)
- Price history: logged on update when price_per_unit changes (parallel with update via Promise.all); never when the old or new price is NULL (price pending)
- **Price pending (RI-0c):** a new ingredient may be saved without a price (`package_price` NULL, ingredient form "Price pending" toggle; package size placeholder 1000 g/ml or 1 buc until a receipt sets it). Prices are never invented. `calculateRecipe` / `calculateDay` / `calculateWeek` / `generateShoppingList` add only priced ingredients and return `unpricedCount` / `unpricedNames` (shopping items carry `unpriced`), so totals and selling price (× markup) are lower bounds shown through `formatCost`. Ingredients list has a "Price pending" filter (`?f=noprice`) and badge; the dashboard lists "N ingredients need a price"; the receipt import shows "No price yet" with no % change and fills the price (no history row).

### Nutrition
- Everything normalized **per 100g/100ml**
- Barcode lookup: `lookupBarcode(code)` in `lib/nutrition/open-food-facts.ts` (OFF v2 API) returns `{ result, packageSize, perServingOnly }`; no NCS hard-reject (user reviews the result). Scan from the ingredient form or the Scan button on the Ingredients page. Camera access requires HTTPS: test on a phone over LAN with `next dev --experimental-https`. The zxing `.wasm` is copied to `public/zxing/` by `npm install` (`postinstall` -> `scripts/copy-zxing-wasm.mjs`; gitignored). **`proxy.ts`'s matcher must keep excluding `.wasm`** (static files never hit the auth proxy), otherwise customers get `/portal` HTML instead of the wasm and scanning silently fails (the scanner now also shows an error when the wasm cannot load).
- Recipe aggregation: `nutrient_total = sum(ingredient_nutrient × (quantity / 100))`
- Per portion = total / portions
- Micronutrients stored as flexible JSONB (vitamin_a_ug, iron_mg, etc.)

### Confidence Scoring (NCS)
```
NCS = completeness(0.3) + verification(0.2) + freshness(0.15) + consistency(0.2) + context(0.15)
```
- USDA: Foundation=1.0, SR Legacy=0.97, FNDDS=0.93, Branded=0.85
- OFF: computed via formula, must be ≥ 0.85 to appear

### Customer diary day (FD-2, `/portal`)
- Sections Breakfast / Lunch / Dinner / Snacks (`components/portal/diary-section.tsx`): plan `MealCard`s + that meal's `food_log_entries` (`diary-entry-list.tsx`, rows editable later via `onSelect`) + a per-section "+ Add" (`onAdd(mealType)`; today opens a stub sheet that FD-3 replaces). Future days show plan meals only, no Add and no eaten toggles; past/today allow logging. The diary works on days with no plan.
- Summary (`diary-summary.tsx`): kcal eaten / target / remaining, P/C/F bars, fiber aim range, and a "Planned" ghost on the kcal bar (projection = eaten + unmarked plan meals). Totals come from `calculateDiaryDay` (eaten = plan meals marked eaten × `portion_factor` + logged entries; skipped never counts); `planEntryNutrition` replaced the old 5-field `entryNutrition`.
- Targets: `resolveDayTargets(plans, client, date)` (`lib/portal/day-targets.ts`) = plan covering the date, else the latest earlier plan, else the client's `calorie_target` only; macros on `target_weight_kg ?? weight_kg`.
- Status writes go through `useMealStatus` (`lib/portal/use-meal-status.ts`): optimistic overlay, batch save (also used by "Mark remaining as eaten", with Undo), rollback + Retry toast, offline-queued. Saves are serialised per entry (a later tap waits for the earlier POST) and an override is dropped as soon as fresh server data arrives unless its save is in flight or queued offline. "Mark remaining as eaten" skips meals whose save is still in flight and sends ONE batch request. Used by Today and the plan detail page; `MealDetailSheet` takes `onChangeStatus` instead of saving itself. `PortionFactorSheet` = "Ate a different amount".
- Local date: the browser stores its IANA timezone in a `tz` cookie (set from `today-client.tsx`); the page computes today with `todayInTz(cookie)` (fallback `Europe/Bucharest`) and the client refreshes once if its own date differs. Logged rows for the day are read with the customer's RLS client; portal reads of ingredients/recipes use the `*_public` views.
- "Go to …" empty-day hint targets the nearest day that has plan MEALS (`mealDates`), not a plan-covered day.

### Container Tracking
- **Container types**: glass containers with name, volume, replacement cost
- **Recipe assignment**: each recipe optionally has a container_type_id
- **Delivery flow**: when delivering a meal plan, containers sent = recipe's container × portions per entry
- **Returns**: on next delivery, expected returns = containers sent in previous delivery
- **Balance**: outstanding = total sent − total returned (per client, per container type)
- **Tolerance**: each client has `container_tolerance` (default 2) — max outstanding before flagging
- **Flagging**: when total outstanding > tolerance → client is flagged (amber warning in dashboard)
- **Charging**: containers beyond tolerance can be charged at replacement cost from `container_types.cost`

### Recipe import (RI-3)
- Page `/recipes/import` (button "Import" in the Recipes header; deep link `?url=`, set with `router.replace`, cleared when a text/screenshot import starts). Admin picks a tab: URL, Paste text or Screenshots (the receipt import's browser-side slicing, shared in `lib/images/slice.ts`; limits 10 parts / 4 MB). `POST /api/recipes/import/parse` is stateless (RI-1 extraction + RI-2 Claude mapping, env `RECIPE_PARSER_MODEL`, default `claude-haiku-5-5`); a blocked site returns the friendly message and the page offers "Switch to Paste text".
- Review: one row per printed line (cards below md, table at md+); section headers are greyed headings, "to taste" lines start skipped, estimates are highlighted; match picker (`IngredientPicker`), amount in the ingredient's unit (decimal comma, `parseDecimal`; a re-picked ingredient with another unit shows a "check it" warning), include/skip, "Skip all unmatched". "Create ingredient" opens `IngredientForm` with `defaults` (capitalised raw name, suggested unit and category, price pending) and the nutrition search prefilled with the line's English `search_term`; `onSaved` matches only that line. Recipe panel: name, portions, container, source link, steps (`RecipeStepsEditor`), customer description; live cost (`formatCost`, incomplete-cost note), per-portion nutrition, piece-weight warnings and "Site says X kcal per portion · calculated Y". A duplicate banner links to `/recipes?edit=<id>` (same normalised `source_url` first, then same name: `findDuplicateRecipe`, `normalizeSourceKey` in `lib/recipes/import/url.ts`).
- Pure logic in `lib/recipes/import/draft.ts` (tested): `initReviewLines`, `canApprove` (name + at least one included line, every included line matched with amount > 0), `buildSavePayload` (skipped/header lines excluded; two lines on one ingredient are summed and the page says so; one alias per matched line whose raw name differs from the ingredient name), `siteCalories`.
- Approve (after a confirm) calls `save_imported_recipe` (recipe + ingredients + aliases with store `recipe`, atomic), invalidates recipes (and ingredients when any were created), then opens `/recipes?edit=<id>`. Discard and leaving with an unsaved draft confirm via `useConfirm()`; a failed save toasts with Retry. Nothing is written before Approve (created ingredients excepted: they are saved through the ingredient form straight away, price pending).

### Invoice import
- Page `/ingredients/import`. Admin uploads Lidl Plus receipt screenshots / Freshful PDFs; tall images are sliced in the browser into ≤1560 px JPEG chunks (120 px overlap), total upload ≤4 MB.
- `POST /api/invoices/parse` is **stateless**: sends files + a compact ingredient/alias catalog to Claude (`lib/invoices/parse.ts`, structured output via zod), post-processes (`lib/invoices/postprocess.ts`: exact store alias overrides the model match with high confidence; unknown ids dropped; unit mismatch nulls the match) and returns lines with current vs new price-per-unit and % change plus a read-only `duplicateOf` check.
- **Approval checkpoint**: the parsed result lives only in client state; nothing is written until the admin reviews/edits lines and clicks Approve, which calls `/api/invoices/apply` → `apply_invoice_prices` (writes `invoices`, logs price history, updates prices, upserts `ingredient_aliases`).
- Label-photo parsing (FD-5, `lib/portal/label-parse.ts`) uses the same SDK pattern with env `LABEL_PARSER_MODEL` (default `claude-haiku-5-5`) and REQUIRED `LABEL_SIGNING_SECRET` (no fallback; label routes return 500 when unset). The model only transcribes (structured output allows at most 16 nullable params, so absent numbers use sentinel -1); all conversions live in the pure `lib/portal/label-map.ts` (per-serving -> per-100, kJ -> kcal, sodium x 2.5 -> salt, micronutrient units, then the shared `validatePer100` from `foods.ts`); `label-sign.ts` signs/verifies the draft; `label-food.ts` has path checks, the 10/day parse limit and the confirm insert.
- Env: `ANTHROPIC_API_KEY` (required), `INVOICE_PARSER_MODEL` (default `claude-haiku-5-5`; `claude-sonnet-5-5` also tested). Calls use the beta Messages endpoint with `output_config.effort: "medium"`; non-Haiku models also send the server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) — Haiku has none.
- Confirmations (Approve / Discard) use an in-page modal, not `window.confirm()`, which some embedded browsers suppress.

### PDF Export
- React PDF document (`@react-pdf/renderer`) generated server-side
- Content: meals by day with full nutrition per meal, daily totals, disclaimer
- **No pricing** shown to client
- Download as PDF or email via Resend (attachment)
- Disclaimer: "Except for protein, fiber, fat, and carbs, nutritional values may contain inaccuracies"

## Design Decisions

| Decision | Choice | Reason |
|----------|--------|--------|
| Nutrition source priority | USDA first, OFF fallback | Raw ingredient accuracy |
| OFF geographic filter | Romania-first, global English fallback | Market-specific products |
| Cooked USDA entries | Filtered out unless query requests | Raw values more accurate for meal prep |
| NCS threshold | Hard reject < 0.85 | Prevent bad data in meal plans |
| Composite foods | Rank lower, not excluded | User may search "mici", "lentil chips" |
| Price history storage | Dedicated table | Queryable, supports trend analysis |
| Price history trigger | App-side on form submit | Simpler than DB trigger, compare price_per_unit |
| Price history display | Collapsible list in edit modal | Contextual, non-intrusive |
| Nutrition values | Rounded to 2 decimals in form | Prevents ugly floating-point display |
| Container tracking | Quantities by type, not individual | Simpler, sufficient for small operation |
| Container returns | Expected vs actual on next delivery | Free breakage/loss tracking |
| Container tolerance | Per-client threshold (default 2) | Friendly buffer before charging |
| PDF export | @react-pdf/renderer | React component model, server-side rendering |
| Email service | Resend | Simple API, free tier, Vercel-compatible |
| PDF content | No pricing, full nutrition + disclaimer | Client doesn't need to see costs |
